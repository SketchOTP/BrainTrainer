## Next substantive development target

Expand the software-improvement loop beyond choosing a practice threshold.
Start with a production-boundary experiment that accepts compositional executable
rules over observed state, while retaining exact source, isolation, candidate
predictions, rejection evidence and continuity. Keep the old policy version
available for historical replay. Do not present a larger fixed lookup table as
general software understanding.

The creature must select an improvement from a recorded limitation, state an
observable expectation, test a separately instantiated candidate on its triggering
case and retained abilities, then compare benefit and cost. Task-derived cases
must complement the authored regression floor. Evaluate at least one new
implementation problem outside the current stopping-rule family before claiming
broader executable development or improved improvement. A development-agent
patch to enable this mechanism is infrastructure, not evidence that the creature
has performed that loop.

A concrete first boundary experiment is the rejected compositional threshold in
current-evidence.json. It is not yet a selected creature proposal or demonstrated
useful change; use it to test representation/execution capability only, then
require experience-originating proposals and transfer evidence. The live
individual was not modified during this audit.
