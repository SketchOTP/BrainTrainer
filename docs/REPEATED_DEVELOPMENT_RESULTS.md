# Developmental v9: repeated executable growth and learned evaluation order

The previous loop could replace a total-attempt stopping rule once, but its own
eligibility condition prohibited another change. V9 admits a second observed
limitation: an interaction has demonstrated progress, then becomes slower than the
uniform no-progress threshold permits. The individual diagnoses the rule that
actually stopped its goal, generates two finite source programs, tests them on
explicit branches, rejects a regression and retains the useful program.

| Stage | Executed rule | Trigger for review |
|---|---|---|
| Initial | Stop after three total attempts | Productive delay-two interaction stops after only one observed effect |
| First retained change | Stop after three consecutive attempts without progress | A second object becomes slower after one actual effect |
| Second retained change | Stop after three attempts without any progress; allow four consecutive non-progress attempts after observed progress | No further source-generation family is implemented yet |

The conditional threshold is compiled executable Python in the same finite AST
boundary. Calls, imports, host access and arbitrary expressions remain outside the
accepted language. Source generation and diagnosis templates are authored. There
is still a ceiling after this second family; this is not general self-coding.

## Prospective behavioral evidence

The protocol in REPEATED_DEVELOPMENT_PROTOCOL.md was written before the panel.
Seeds 141–144 each completed two experience-initiated executable revisions in one
continuing individual. All four preserved their complete prior event prefix,
identity and branch. Each finished the second learning goal and then demonstrated
the first learned skill on a new target. Restoration preserved subsequent behavior;
a separate real CLI process reproduced the final complete state for seed 141.

The second overbroad candidate increases the no-progress threshold globally and
fails the inert-object regression. The selected program preserves the original
first-contact bound while allowing an extra attempt after demonstrated progress.
It passes all eight mandatory profiles, including prior skills, slower initial
interactions, a previously productive object becoming inert and an unfamiliar
interaction becoming slower after progress.

There is a real cost: when a previously productive object becomes inert, the new
rule spends four consecutive unsuccessful attempts instead of three. The protocol
makes that cost explicit. Completely unfamiliar devices that require more than
three attempts before any effect remain unresolved and can require assistance.
External changes to test objects are attributed environmental interventions, not
claimed actions or discoveries of the creature.

## Experience improves candidate evaluation

The curriculum owns a projection of which test profiles rejected earlier
candidates, with references to the original evaluation events. V9 uses that history
to order mandatory tests. It may stop testing a rejected candidate after a failing
regression and explicitly records untested profiles. An accepted candidate must
pass every required profile. No prior success substitutes for a new test.

A paired ablation starts from the identical second-limitation checkpoint and
removes only use of evaluation-history ordering. Both arms retain early rejection
and the same mandatory suite. They select the identical source digest, leave the
continuing parent unchanged and run all eight checks for the accepted program.

| Completed evaluation measure | Ordering memory ablated | Learned ordering |
|---|---:|---:|
| Test cases executed | 14 | 9 |
| Actual test-branch ticks | 62 | 43 |
| Accepted-candidate cases | 8 | 8 |
| Elapsed seconds | 3.673 | 2.476 |
| CPU seconds | 3.672 | 2.476 |
| Peak process RSS KiB | 40,676 | 40,148 |

The completed task loads the checkpoint, evaluates candidates, verifies parent
preservation and complete acceptance coverage, and writes the full test report.
Runs used separate fresh processes sequentially after regression testing, with no
child processes. Imports are excluded; OS caches and other host activity were not
controlled. Agent token cost was not measured. This one comparison shows 31% fewer
branch ticks and about 33% less CPU; it does not establish a general speedup.

This is a causal demonstration of experience-informed evaluation efficiency. The
mechanism for learning test order is authored, not an executable procedure the
creature invented or rewrote. It is separate evidence from the two successful
practice patches, and remains narrower than the complete improve-improvement goal.

## Verification and deployment boundary

All 81 related regression checks passed in 115.552 seconds. The three new tests
cover repeated code adoption and retained skill, evaluation-memory ablation with
unchanged acceptance, and execution/rejection at the expanded source boundary.
A preserved v8 checkpoint produced identical complete state after 16 ticks under
preserved and current code. The request's explanatory objective text was clarified
after qualification to state the extra-attempt tradeoff; executable behavior was
unchanged.

Evidence is in `validation/repeated-development/`; source before-images are in
`validation/repeated-development-before/`. All 267 pinned original files remain
unchanged. The visible v6 individual remains paused and durable at tick 93, with
its original identity and branch. V9 is a candidate, not a live adoption.

The full goal remains incomplete: broader self-understanding and code generation,
long-life capacity, richer independent activity, shared-history companionship and
sustained owner acceptance still require integrated evidence.
