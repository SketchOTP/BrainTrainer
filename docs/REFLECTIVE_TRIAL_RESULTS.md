# Reflective proposals to lived trials — candidate v33

The reflective worker now requests a machine-readable trial alongside its concise
hypotheses and proposed goal: observed target/type/action, optional exact starting
and expected appearance, attempt allowance and world-time allowance. This does
not infer executable semantics from free prose.

A continuing individual can admit a practice proposal as a hypothesis event.
Admission adds no experience and changes no host body state. The developmental
executive then selects approach/contact/interaction through the existing body.
Maintenance retains priority. Unrelated automatic code evaluation is deferred
while the trial is active; the evaluator cannot silently change the software
under the trial.

Results derive only from matching executed actions and actual outcomes:
- completed interaction plus the predicted visible change: observed-success;
- attempt limit without the prediction: prediction-not-observed;
- missing/changed target, unavailable action, or exhausted world-time allowance:
  incomplete, with a reason;
- an observed adverse hunger consequence: adverse-result-stop.

An observed success means the specified prediction matched this trial. It does
not certify general competence. The retained full event history remains the
source for learning and later review. Dreaming or accepting a proposal adds no
successful outcome. An exact expected appearance is distinct from any visible
change. Changed starting circumstances are rechecked at execution.

Thirteen current unit/integration checks passed in 10.791s. They cover actual
body success/nonresponse, missing target, changed start, approach timeout,
nonmatching prediction, invalid/duplicate admission, no automatic patch during
trial, proposal boundary failures, report regressions and exact restore with
matching subsequent actions. Receipts: validation/reflective-trials/.

Candidate v33 is not adopted. Live v32 remains unchanged. Automatic reflection
scheduling, acceptance of finished asynchronous jobs, visible trial goals/outcomes,
and a live trial still need qualification. Broader goal types, code commissioning,
built-in sprite generation and environment-agent generation remain unfinished.

## Actual OAuth proposal and body execution

Executed validation/reflective-trials/oauth_trial.py. An explicit qualification
fork with an unresolved, experience-originating toy goal was reflected on through
the real OAuth CLI. The returned proposal specified the observed toy/type, action
1, a two-attempt allowance and four-world-tick limit. It was admitted without
rewriting the proposal. The actual body then completed one interaction, observed
the appearance change and recorded observed-success after one world tick. The
outcome event followed the hypothesis event and was an experience record. Full
checkpoint restoration matched exactly.

The provider used 17,584 input tokens and 492 output tokens. Request, response,
usage receipt, actual body result and final checkpoint are retained under
validation/reflective-trials/oauth-01/. This proves the proposal-to-body plumbing
in a developer qualification run. It is not a live individual's learned lesson,
autonomous scheduling, or proof of improved general competence. No test records
were imported into the main habitat.
