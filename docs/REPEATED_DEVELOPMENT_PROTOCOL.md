# Repeated executable development protocol

Candidate v9 preserves prior versions and extends the finite practice language
with a progress-sensitive stopping rule. The continuing individual first learns
that counting total attempts interrupts productive delayed interactions. Later a
different object becomes slower after its first observed effect, exposing the
limitation of a uniform no-progress threshold. Each review must arise from the
creature's own goal/outcomes, not an externally requested patch.

Prospective seeds 141–144: learn an opaque delay-two object through the first
code revision; introduce a new type, initially delay two; after its first real
effect change its delay to four through an attributed external intervention.
The second failure must initiate another executable proposal. Reject a globally
longer threshold on the inert-object regression; accept a threshold extended only
after real observed progress. Preserve previous history, first learned ability,
identity and branch across both changes and restoration.

A learned evaluation schedule may prioritize profiles that rejected earlier
candidates. Failed candidates may stop early with explicit incomplete coverage;
accepted candidates must pass every required profile. Compare the second evaluation
with an ablation of only that schedule. Selection and mandatory coverage must agree;
actual branch ticks/cases should decrease when prior failures are useful. This is
experience-informed evaluation, not general recursive code improvement.

The second policy permits one extra failed attempt after observed progress. Include
a productive object that becomes inert and a held-out slower-after-progress object
to expose that cost and generalization boundary. No experience in a test branch
counts as continuing-individual competence. Preserve failures and negative results.
